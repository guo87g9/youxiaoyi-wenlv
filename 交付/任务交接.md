**推送过程中踩到的四个坑（留给后来人）**

1. **沙箱与浏览器隔离**：你在自己电脑上登录 GitHub，沙箱这个独立容器拿不到登录态。
   `gh auth status` / `git credential` / 连接器三条路都是空的，必须由账号持有人提供 PAT。
2. **PAT 必须填 Note**：GitHub 生成 classic token 时 Note 必填，空着会报 `Note can't be blank`，
   生成按钮是灰的。填任意名字即可。
3. **token 缺 `workflow` scope**：只有 `repo` 权限时，用 API 写 `.github/workflows/` 会被拒绝，
   写普通文件却可以（所以当时 `_apitest.txt` 能成功、`pages.yml` 返回 404）。
   因此 Pages 最终没走 Actions workflow，而是改用 **`docs/` 目录直接发布**，同一效果且更省事。
4. **沙箱到 github.com 的 443 端口间歇性不通**（`GnuTLS recv error -110` / 连接超时 132s），
   但 `api.github.com` 一直稳定。重试即可；实在不行可用 API 逐文件提交。

**Pages 发布策略**：`docs/` 由 `tools/build.py` 自动生成（前端运行文件 + 图片，**跳过 15 MB 音频**，
写入无密钥的占位 `config.js`），体积 1.08 MB / 42 文件。线上版地图降级为手绘示意，
完整体验请用 `交付/` 下的单文件版。

**安全**：token 只在推送瞬间注入 URL，推完立即从 remote 摘除；已确认
`git config --local`、`--global`、`.git/config` 三处均无残留。
`app/config.js`（含天地图 key）自始至终未进入版本库，远端只有 `config.example.js`。

### 5.1.1 天地图 key：不需要加白名单（实测已排除）

之前担心"白名单没配导致地图发白"，实测是误判：

```bash
# curl 直接请求会 403，但这是天地图对「浏览器端 key」的保护，不是白名单问题
{"resolve":"Key权限类型为:浏览器端，请使用浏览器访问！","msg":"权限类型错误","code":301012}
```

用真实浏览器打开交付件，进入「护照」页（地图所在页）实测：

| 检测项 | 结果 |
|---|---|
| 天地图瓦片请求 | **16 个请求全部 200** |
| 地图 canvas | 1 个，尺寸 362 × 285 |
| 渲染内容 | 真实底图：河道、路网、地名、比例尺齐全 |
| console / pageerror | 0 |

结论：**key 有效、无需任何后台配置**。403 只是服务端 curl 没有浏览器上下文。
